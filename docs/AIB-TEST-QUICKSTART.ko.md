# `aib test` 시작하기: 바뀐 테스트만 다시 실행

> 처음 사용하는 분을 위한 안내입니다. 한 문장으로 요약하면 **테스트가 읽은 파일과 실행 환경이 하나도 바뀌지 않았다면 지난번 녹색 결과를 재사용하고, 빨간색은 항상 다시 실행하며, 측정할 수 없는 것도 항상 다시 실행합니다.**
> 따라서 실수가 있더라도 최악의 경우는 "절약 없음"일 뿐이며, 깨진 코드를 정상으로 보고하는 일은 없습니다.

## 1. 실행 방법

```bash
aib test tests/test_foo.py tests/test_bar.py      # 이 테스트들을 실행합니다(가능하면 재사용)
aib test --fresh tests/test_foo.py                # 이번에는 전부 실제로 실행합니다(결과는 여전히 기록)
aib test --why tests/test_foo.py                  # 실행하지 않고, 재사용될지와 어떤 파일 때문에 막히는지만 알려 줍니다
aib test --repo ~/my-project tests/test_x.py      # 다른 저장소에서 실행합니다
aib test --estimate                              # 실행하지 않고, 이 저장소의 최근 커밋 50개로 커밋당 절약량을 추정합니다(이전 실행 1회 필요)
```

테스트마다 한 줄씩 `✓ … (reused the last green result)`, `▶ … running`, `└ green` / `└ ✗ RED`가 출력되고, 마지막 줄은 합계입니다. 빨간 테스트의 출력은 마지막 표 아래에 표시됩니다.

### 자신의 프로젝트에서 사용하기(프로젝트 전용 가상 환경 사용)

```bash
cd ~/my-project
source .venv/bin/activate                          # 또는: 저장소에 .venv/ 또는 venv/가 있으면 자동으로 사용되므로 활성화할 필요가 없습니다
pip install pytest -e .                            # 프로젝트와 테스트에 필요한 모든 것을 이 환경에 설치합니다
aib test --repo . tests/test_*.py
```

사용되는 python의 우선순위: `AIB_TEST_PYTHON=<path>` > 저장소의 `.venv/` 또는 `venv/` > 활성화된 `VIRTUAL_ENV` > aib 자체의 python.
aib 자체의 python이 아닐 때는 시작 시 다음 줄이 출력됩니다: `ℹ Test python: … (version …; pytest …; from: …)`.
해당 python의 버전과 pytest 설치 여부는 "실행 환경"에 포함되므로, 이를 바꾸면 모두 다시 실행됩니다. 패키지를 업그레이드해도 마찬가지입니다(읽는 패키지 파일이 바뀌었기 때문입니다).
실측(itsdangerous, 테스트 5개): 1회차 3.2초로 전부 실행, 2회차 0.4초로 전부 재사용, `signer.py`를 한 줄 고치면 ⇒ 5개 모두 다시 실행되었습니다.

외부 프로젝트 실측(10개, 모든 경우에 빨강/녹색이 pytest 직접 실행 결과와 일치): itsdangerous, markupsafe, more-itertools, click, dateutil,
Flask(19.5 → 5.3초), requests, django-taggit(46 → 12초), pytest-xdist(99 → 74초), humanize(12 → 2.4초).
모두 라이브러리이며, 모두 Linux에서만 측정했습니다.

## 2. 지원하는 테스트

| 종류 | 실행 방식 | 상태 |
|---|---|---|
| Python, 파일이 `if __name__ == "__main__":`로 끝남 | 직접 실행 | 안정 |
| Python, pytest 스타일(위 블록 없음, `class TestXxx:`, `async def test_` 포함) | 해당 python에 pytest가 있으면 pytest, 없으면 내장된 작은 실행기가 `test_*` 함수를 실행 | 사용 가능. pytest fixture를 쓰는데 pytest가 설치되어 있지 않으면 ⇒ 설치하라는 메시지와 함께 빨간색으로 표시 |
| Node(`.js` `.mjs` `.cjs`, `node:test` 사용) | `node <file>` | 첫 버전(공통 인수 사례 12개 모두 통과) |
| jest / mocha를 쓰는 JS/TS(루트 package.json에서 감지, `node_modules/.bin/` 설치 필요) | jest: `--runInBand --no-watchman`, 한 번에 파일 하나; mocha: `mocha <file>` | 사용 가능(luxon 테스트 23개와 cliui: 빨강/녹색이 프레임워크 직접 실행과 일치, 2회차에 녹색은 모두 재사용) |
| vitest를 쓰는 JS/TS | `vitest run --pool=forks <file>` | 올바르게 실행되지만 **측정할 수 없어 매번 다시 실행**: vitest 4 / vite 8은 트레이서가 볼 수 없는 네이티브 코드로 파일을 찾습니다 |
| bash 스크립트(Python/Node 테스트가 시작한 것) | 부모 프로세스를 따름 | 안정 |
| Go(저장소 루트에 `go.mod`, `*_test.go`) | `go test ./<that file's directory>`, Go 자체 캐시 사용(이 머신의 실제 GOCACHE / GOMODCACHE) | 사용 가능(google/uuid: 테스트당 약 0.25초, 코드를 깨뜨리면 ⇒ 모두 빨강). 패키지 단위로 동작: 같은 디렉터리의 파일은 함께 빨강/녹색이 되며, 모듈은 먼저 내려받아야 합니다(`go mod download`) |
| PHP(composer.json에 phpunit, `tests/` 아래 `*Test.php`) | `php vendor/bin/phpunit <file>`(먼저 `composer install` 실행) | 사용 가능(sebastian/diff 테스트 17개, 빨강/녹색이 phpunit 직접 실행과 일치). 트레이서가 읽을 수 없으므로 ⇒ 항상 실제로 실행 |
| 기타 언어(Ruby, Rust, Java…) | `.aib/ship.toml`에 선언: `[test]` `files = ["spec/**/*_spec.rb"]`, `command = "bundle exec rspec {file}"`(`{file}`은 해당 테스트의 상대 경로로 치환) | 트레이서가 읽을 수 없으므로 ⇒ 항상 실제로 실행되지만, 패키지 푸시·릴리스·원인 순위는 모두 동작. Ruby(minitest/rspec), Go, JS는 "아무것도 실행되지 않음"을 뜻하는 요약 줄을 인식하여 ⇒ 미검증으로 표시(minitest로 테스트함) |

## 3. 결과가 재사용될 때와 항상 다시 실행될 때

항상 다시 실행되는 경우:
- 지난번에 빨강, 시간 초과, 또는 불안정(같은 조건에서 빨강이 된 적 있음)이었던 경우.
- 테스트가 읽은 파일의 내용이 바뀌었거나, 나열한 디렉터리에 파일이 추가·삭제되었거나, 찾았지만 없었던 파일이 이제 존재하는 경우.
- 실행 환경이 바뀐 경우(언어 버전, 환경 변수, 패키지 잠금 파일).
- 네트워크에 접근했거나, 측정할 수 없는 프로그램을 시작한 경우(훅이 없는 언어, 강제 종료된 자식 프로세스).
  데이터베이스: C로 작성된 드라이버(psycopg2, mysqlclient, grpc, pyzmq, pycurl…)는 Python의 socket을 거치지 않고 자체적으로 연결을 열기 때문에,
  불러오기만 해도 네트워크 접근으로 간주합니다. (이전 버전은 이를 놓쳐서 ⇒ 데이터베이스 내용이 바뀌어도 결과가 재사용되었습니다.) 순수 Python 클라이언트는 socket을 거치므로 항상 감지되었습니다.
- 기록이 만료된 경우: 처음에는 3일이며, 다시 실행해도 여전히 녹색이면 기간이 두 배(6일, 12일)로 늘어나 최대 14일까지 늘어납니다.
- 테스트가 읽은 파일에 날짜가 들어 있고, 마지막 실행 이후 그 날짜가 지난 경우.

**번역 파일은 문자열 단위로 추적합니다(설정 불필요)**: 프로젝트가 gettext로 번역할 때(Django, Flask-Babel, babel 모두 해당),
gettext로만 텍스트를 조회하는 테스트는 **자신이 사용한 특정 문자열**이 바뀔 때만 다시 실행되며, 다른 문자열을 고치거나 새 문자열을 추가하면 ⇒ 재사용됩니다.
테스트가 .mo 파일을 직접 읽거나, 카탈로그 전체를 열거하거나, 번역 파일이 깨져 있으면 ⇒ 이전처럼 파일 전체를 기준으로 판단합니다(다시 실행). .mo는 .po에서 컴파일되므로 .po를 고친 뒤에는 먼저 .mo를 다시 컴파일하십시오.

사전을 JSON으로 관리하고 조회 함수를 직접 작성하는 프로젝트: `.aib/ship.toml`에 어떤 파일이 사전인지 선언합니다(패턴은 저장소 루트 기준 상대 경로):

```toml
[test]
keyed_files = ["locales/*.json"]
```

그 후 테스트가 이 파일들을 `json.load` / `json.loads`로 읽고 일부 키만 사용하면 ⇒ 해당 키(그 아래의 값 트리 전체 포함)가 바뀔 때만 다시 실행됩니다.
전체를 비교·열거·복사·문자열화하거나, 파싱 전에 내용이 변경된 경우(예: Windows 줄바꿈 변환) ⇒ 이전처럼 파일 전체를 기준으로 판단합니다. 선언하지 않은 JSON은 항상 파일 전체를 기준으로 합니다.

## 4. 세 가지 스위치

- 이번 회차에 전부 실제로 실행: `AIB_TEST_NO_REUSE=1 aib test …`
- 특정 테스트를 항상 실제로 실행: 테스트 파일의 처음 40줄 안에 `# aib: always-run`을 넣습니다
- 이 머신에서 할 수 없는 것은 실행하지 않음("⊘ unverified"로 표시되며 녹색도 빨강도 아닌 것으로 집계): 테스트 파일의 처음 40줄 안에 다음을 넣습니다
  `# aib: needs darwin`, `needs linux`, `needs ipv6`, `needs tool:<program>`, `needs repo:<name of a sibling repo>`
  ★ 조건에는 테스트의 *전제 조건*만 적어야 하며, *테스트 대상 그 자체*를 적어서는 안 됩니다. 그렇지 않으면 그것이 없을 때 테스트를 건너뛰어 문제를 숨기게 될 뿐입니다.

## 5. "미검증"은 항상 드러납니다

- `⊘ … (unverified: this machine lacks …)`: 이 머신에 전제 조건이 없어 실행하지 않았습니다. 요약 표에 별도 줄로 표시되며, 배치는 종료 코드 4로 끝납니다.
- `⊘ N cells skipped, unverified`: 녹색 테스트에 건너뛴 케이스(`skip`)가 있습니다. 요약 표에 별도 줄로 표시됩니다.
- 종료 코드: 0 모두 녹색, 1 일부 빨강, 3 기록이 저장되지 않음, 4 일부 미검증.

## 6. main으로 푸시하고 릴리스하기: `aib ship`(모든 프로젝트에서 동작, 설정 불필요)

사용자를 위한 쉬운 안내서(매번 무엇이 보이는지, 어떻게 읽는지, 어떻게 하면 가장 많이 절약하는지): `AIB-SHIP-FOR-USERS.ko.md`.

```bash
cd ~/my-project
aib ship init                     # 새 사용자의 첫 단계: 프로젝트 이름과 트리를 보여 주고, 버전과 테스트를 찾고, 테스트가 이 트리를 테스트하는지 확인하고,
                                  #   전체를 한 번 실행해 기록을 만들고, 앞으로의 절약량을 추정하고, 가장 많은 테스트에 영향을 주는 파일을 나열합니다.
                                  #   푸시나 커밋은 하지 않습니다(--no-run은 감지만 합니다)
aib ship package --preview        # 실행·푸시하지 않음: 재사용될 것으로 예상되는 테스트 수, 걸릴 시간, 주된 원인 파일
aib ship hotfiles                 # 많은 테스트가 읽고 자주 바뀌는 파일 10개(읽는 테스트 수 × 최근 변경 횟수): 이 파일들의 변경을 한 번의 푸시로 모으면 가장 많이 절약됩니다
aib ship package                  # origin의 main으로 패키지 하나를 푸시: 버전 규칙 → 수정에는 테스트가 따라야 함 → 푸시 전 검사 → 푸시
aib ship watch                    # 개발하는 동안 켜 두기: 저장을 멈추고 10초 뒤 미러 트리에서 테스트를 실행합니다(작업 디렉터리는 건드리지 않음). 푸시할 때 그 결과를 재사용합니다
aib ship stats                    # 첫 실행 이후 누적 합계(전체 테스트/케이스, 실행별·주별 실제 절약량) + 언제 푸시하면 가장 많이 절약되는지와 해야 할 일
# 푸시 전 검사는 먼저 비교를 보여 줍니다: aib 없이(테스트를 하나씩) 걸리는 시간, 이 머신에서 aib로 걸리는 시간(과 끝나는 시각), 머신을 늘렸을 때의 예상치.
#   끝나면 정산합니다(나란히 실행해서 절약한 양 / 섀도 재개로 추가 절약한 양)
aib ship stats --all              # 이 머신의 프로젝트마다 한 줄(전체 테스트/케이스, 푸시 횟수, 절약량) + 총합계
aib ship audit                    # "재사용된" 테스트 일부를 실제로 다시 실행해 결과를 비교합니다(재사용이 올바른가?). 결과는 합계에 반영되고 주별로 표시됩니다
aib ship stale [--run]            # 7일 넘게 실제로 실행되지 않은 테스트(푸시 전 검사는 영향받는 테스트만 고르므로 건드리지 않은 테스트는 오래 실행되지 않을 수 있고, 빨강이 그곳에 숨습니다).
                                  #   --run은 이들을 한 번에 실행합니다. 매주 권장(한 번의 일괄 실행에서 테스트 5개가 줄곧 빨강이었고 14개는 클라우드에서 한 번도 실행된 적이 없었습니다)
aib ship why                      # "항상 다시 실행해야 하는" 테스트를 원인별로 순위화(개수, 회차당 소요 초)하고 쉬운 설명과 해야 할 일을 보여 줍니다
aib ship crosscheck               # 전체 스위트와 대조: aib는 테스트를 하나씩 실행합니다. 이 명령은 먼저 하나씩 실행한 뒤(가능하면 재사용) 프로젝트의 평소 방식으로 전체 스위트를 한 번 실행하고,
                                  #   파일별로 빨강/녹색을 비교합니다. 불일치 = 테스트끼리 영향을 주고받음(공유 상태, 실행 순서). 즉 aib의 녹색이 전체 CI 실행의 녹색을 뜻하지는 않습니다.
                                  #   pytest, jest, vitest, mocha 지원. 종료 코드 0 일치 / 1 불일치 / 4 비교 불가. 매주 권장
aib ship check                    # main 이력에서 규칙을 어긴 커밋을 검사합니다(CI용)
aib ship release --version 1.4.0  # 터미널 앞의 사람만 가능: 먼저 미리 보기, 버전을 입력한 뒤에만 릴리스
aib ship package --emergency      # 터미널 앞의 사람만 가능: 사유를 입력하면 푸시 전 검사를 한 번 건너뜁니다. 다음 패키지는 자동으로 검증되며, 그때까지 릴리스할 수 없습니다
```

- **어떤 파일을 테스트로 간주하는가**: Python은 `tests/` 아래의 `test_*.py`, `*_test.py`, `test-*.py`. **pytest에 `testpaths`가 설정되어 있으면 그 경로만 해당합니다**
  (예: Flask의 `examples/`는 별도로 설치하는 예제이며 pytest도 실행하지 않습니다). JS/TS(저장소 루트에 `package.json`)는 `*.test.*`, `*.spec.*`, 그리고
  `__tests__/` 아래의 파일. mocha 프로젝트는 `test/` 바로 아래의 `.js/.mjs/.cjs`도 포함합니다.
- **버전을 자동으로 찾는 위치**: `VERSION` → `pyproject.toml` → `package.json` → `setup.cfg` → 단일 `__version__`.
  첫 푸시 때 찾은 내용을 `.aib/ship.toml`에 기록하며(해당 패키지에 커밋 하나로 추가), 이후에는 이 파일을 따릅니다. 직접 수정할 수 있습니다. 찾지 못하면 ⇒ 릴리스는 할 수 없지만 패키지 푸시는 평소대로 됩니다.
- **패키지는 버전을 바꿀 수 없습니다**. 버전은 `release`(사람)만 바꿉니다. 따라서 일반 푸시는 영향받는 테스트만 실행하고, 버전은 배치당 한 번 올라갑니다.
- **코드는 바뀌었는데 테스트가 바뀌지 않았으면 ⇒ 푸시하지 않습니다**. 단, 커밋 메시지에 `No-Test-Reason: <reason>` 줄이 있으면 예외입니다(순수 리팩터링, 텍스트만 변경).
- **푸시 전 검사**: 실패할 가능성이 높은 테스트를 먼저 실행하고 첫 빨강에서 멈춥니다. **빨강이 하나라도 있으면 푸시를 막습니다**(aib 자체 저장소의 예외: main에서도 빨강인 기존 빨강은 통과시킵니다).
  새 빨강은 같은 코드에서 한 번 더 실행하며, 녹색이 되면 "간헐적"으로 표시합니다(그래도 푸시하지 않음). 끝나면 가장 느린 테스트 10개와 추정 절약량을 출력합니다.
- **재부팅 후에는 같은 명령을 다시 실행하십시오**: 같은 코드에서 이미 녹색인 테스트는 다시 실행되지 않습니다.
- **테스트한 것이 푸시할 코드가 아니면 ⇒ 푸시하지 않습니다**: 테스트 python이 이 트리 밖에서 패키지를 불러오면(공유 venv, 다른 클론을 가리키는 `pip install -e`) ⇒
  푸시 전 검사가 즉시 "미검증"으로 보고합니다. 프로젝트 전용 `.venv`를 만들고 `pip install -e .`을 실행하거나 `AIB_TEST_PYTHON`을 설정하십시오.
  `pip install -e .`로 설치한 프로젝트는 패키지를 푸시할 수 있지만 `aib ship watch`는 사용할 수 없습니다(미러 트리가 미러 안의 코드를 테스트할 수 없으며, 그렇다고 알려 줍니다).
- **잘못된 릴리스가 나갔을 때**: 잘못된 커밋을 `git revert`하여 패키지 하나로 푸시하고(수정에는 테스트가 필요하다는 규칙은 여전히 적용), 사람이 다음 버전을 릴리스하게 하십시오. 버전을 되돌리지 마십시오.

## 6.5 CI에서 재사용하기: GitHub Actions 사용 시간 절약

GitHub의 머신은 분 단위로 과금되며 사용 시간은 빠르게 소진됩니다. 자체 머신(self-hosted runner) 없이도 절약할 수 있습니다. 명령 하나로 워크플로 파일이 생성됩니다:

```bash
aib ship ci            # .github/workflows/aib-test.yml을 작성합니다(기존 파일은 덮어쓰지 않음. --force는 다시 작성, --print는 출력만)
```

여전히 GitHub의 머신에서 실행되며, 다음 방식으로 절약합니다:

| 절약하는 곳 | 방법 |
|---|---|
| 영향받지 않은 테스트는 실행하지 않음 | aib의 기록 풀을 GitHub 캐시에 저장하므로(같은 브랜치 우선, 다음은 기본 브랜치) 다음 실행에서 지난번 녹색을 재사용합니다 |
| 일어나지 않아야 할 실행은 일어나지 않음 | 기본 브랜치로의 푸시와 PR에서만 실행. `docs/` 또는 `*.md`만 바뀐 경우는 실행하지 않음. 같은 브랜치에 새로 푸시하면 이전 실행을 취소 |
| 설치도 저렴해짐 | pip / npm 다운로드를 캐시합니다(작은 프로젝트는 테스트보다 설치에 대부분의 시간을 씁니다) |
| 얼마나 절약했는지 볼 수 있음 | `aib test --all` 후 각 실행의 요약 페이지(Actions 웹 페이지에서 해당 실행의 Summary)에 "Without aib → with aib"와 세 줄이 추가됩니다: **과금 시간**(GitHub은 작업마다 분 단위로 올림하므로, 작은 프로젝트는 몇 초를 절약해도 과금 시간은 줄지 않는 경우가 많음), "재사용"의 의미, 이번에 실제로 실행된 테스트 |

**다른 사람의 PR(aib를 쓰지 않는 기여자)**:
- 기여자는 aib를 설치할 필요가 없습니다. 요약 페이지에는 "재사용 = 이 테스트가 읽는 모든 파일이 바뀌지 않았으므로 지난번 녹색이 여전히 유효함. 바뀐 테스트, 새 테스트, 이전에 빨강이었던 테스트는 항상 실행됨."이라고 표시됩니다.
- **PR은 캐시를 읽기만 하고 쓰지 않습니다**: 기본 브랜치로의 푸시와 주간 전체 실행만 캐시를 씁니다 ⇒ PR이 많아도 main의 기록을 밀어낼 수 없습니다.
- **포크에서 온 PR은 aib를 쓰지 않고 평소 방식으로 전부 실행합니다**(`python -m pytest` / `npm test` / `go test ./...` / `vendor/bin/phpunit`):
  포크는 시크릿을 받을 수 없고, PR의 테스트 코드가 기록 풀과 같은 머신에서 실행되므로 기록 파일을 다시 써서 그 실행에 대해 자신의 "재사용된 녹색"을 위조할 수 있습니다.
  main은 영향을 받지 않지만(main은 PR이 쓴 캐시를 읽을 수 없음) 리뷰어는 가짜 녹색을 보게 됩니다 ⇒ 포크는 절대 재사용하지 않습니다.
- **매주 일요일에 한 번 전부 실제로 실행합니다**(`--fresh`): 소요 시간을 갱신하고, "오랜 재사용에 가려진" 간헐적 빨강 테스트를 잡아냅니다.

CI 실행 2회를 시뮬레이션했습니다(매번 같은 경로로 새로 클론하고, 두 실행 사이에는 캐시만 기록 풀을 전달. itsdangerous, 테스트 5개):
1회차 6.5초(전부 실행하고 기록 생성) → 2회차 0.9초(5개 모두 재사용, 요약 페이지에 "3.8 s less waiting, about 81%" 출력). 누적 합계는 캐시와 함께 이어집니다.
**실제 GitHub Actions에서는 아직 실행하지 않았습니다**(로컬 시뮬레이션만 했습니다).

- `aib test --all`: aib ship과 같은 방식으로 찾은 모든 테스트를 실행합니다(pytest testpaths, JS/Go/PHP, `.aib/ship.toml` 선언).
  **테스트를 하나도 찾지 못하면 ⇒ 종료 코드 2**(아무것도 테스트하지 않았는데 CI가 녹색이 되어서는 안 됩니다).
- aib 자체는 커밋 하나에 고정됩니다(파일 안의 `AIB_REF`). aib 새 버전은 모든 기록을 한 번 무효화하므로, 고정하지 않으면 aib를 업데이트할 때마다 전부 다시 실행됩니다.
  로컬 aib에 아직 GitHub에 푸시하지 않은 커밋이 있으면 ⇒ 작성하지 않습니다(CI가 가져올 수 없기 때문입니다). aib 저장소가 비공개이면 ⇒ 프로젝트의 Settings → Secrets에 `AIB_TOKEN`을 추가하십시오.
- 설치 줄(`pip install -e . pytest` 같은 것)은 추측입니다. 프로젝트에 맞게 고치십시오.
- **경로가 같아야 합니다**: aib는 git 디렉터리의 실제 경로로 저장소를 식별합니다. GitHub Actions와 GitLab CI는 매번 같은 경로로 체크아웃합니다.
  자체 CI가 매번 다른 디렉터리 이름을 쓰면 아무것도 재사용되지 않습니다(결과는 여전히 정확하며 절약만 없습니다).
- **다른 브랜치가 쓴 캐시를 main이 쓰지 않게 하십시오**: 기록 풀의 "지난번 녹색"이 테스트를 건너뛰게 하는 근거입니다. GitHub의 캐시는 브랜치별로 격리되어 있으며
  (main은 PR이 쓴 캐시를 읽을 수 없음) 생성된 파일은 이에 의존합니다. 다른 CI 시스템은 직접 확인하십시오.
- 빨간 실행도 캐시됩니다(빨간 행은 항상 다시 실행되고, 녹색 테스트는 다음에 재사용될 수 있습니다).
- 캐시가 없는 첫 실행 ⇒ 전부 실제로 실행됩니다. 머신 환경이 바뀌면(python 버전, 패키지, GitHub runner 이미지 업데이트) ⇒ 로컬과 마찬가지로 전부 다시 실행됩니다.
- GitHub 캐시는 저장소당 용량 제한이 있고 한동안 쓰지 않은 항목은 제거됩니다. 제거되면 다음 실행은 전부 실제로 실행됩니다.

## 7. 아직 지원하지 않는 것 / 주의 사항

- 테스트가 **시계만 읽고 파일은 읽지 않는** 시간 의존성(예: "30일이 지나면 만료로 간주")은 기록 만료로만 대응하므로, 알아차리기까지 최대 14일이 걸릴 수 있습니다.
- Node: worker_threads와 네이티브 애드온(`.node`)은 항상 측정 불가로 처리합니다. 컴파일 캐시를 거쳐 실행되는 TypeScript는 검증하지 않았습니다.
- **파일을 직접 읽는 C 라이브러리**(Python의 open을 거치지 않아 트레이서가 볼 수 없음): 이미 처리한 것은 lxml(parse/iterparse), OpenCV(imread),
  pyarrow(parquet/csv/feather/dataset 읽기)로, 경로로 읽을 때 파일이 기록됩니다. h5py, netCDF4, PyTables, GDAL/rasterio/fiona, soundfile은
  불러오는 즉시 측정 불가로 처리합니다(매번 다시 실행).
  **목록에 없는 C 확장**: C 컴파일러가 있는 Linux에서는 aib가 각 테스트 프로세스에 작은 라이브러리를 붙여(안전망, LD_PRELOAD) C 수준의 파일 열기를 기록하고
  나중에 비교합니다. "C 수준에서 Python이 기록하지 않은 저장소 내 파일을 읽음" ⇒ 해당 테스트는 매번 다시 실행됩니다(`aib ship why`가 파일 이름을 알려 줍니다).
  macOS, 컴파일러가 없는 경우, 또는 Go처럼 libc를 우회하는 프로그램 ⇒ 안전망이 없으며, 목록에 없는 C 확장은 알려진 제약으로 남습니다. 끄려면: `AIB_NATIVE_GUARD=0`.
  Node 프로세스도 비교합니다. 다만 Node는 모듈을 해석할 때 훅을 거치지 않고 `node_modules/**/package.json`을 읽으므로, 이 부분은 잠금 파일에 맡깁니다(잠금 파일이 바뀌면 전부 다시 실행) —
  **잠금 파일은 그대로인 채 node_modules 안의 파일을 직접 수정하면** aib가 알아차리지 못할 수 있습니다(알려진 제약).
- Windows는 지원하지 않습니다.
- git을 호출하는 테스트: 이력 읽기(log/show/cat-file/ls-tree…, 리비전이 HEAD의 조상인 경우), 작업 트리 읽기(status/diff/grep), 설정 읽기,
  브랜치/태그 이름 지정은 모두 측정할 수 있습니다. 저장소를 수정하는 것(commit/add/checkout…), 다른 저장소를 대상으로 하는 것, `--ignored`처럼 저장소 밖을 읽는 것은 측정 불가로 처리합니다.
- PYTHONPATH를 통째로 바꾼 뒤 python 하위 프로세스를 시작하는 테스트: 트레이서가 자동으로 맨 뒤에 자신을 추가합니다. 테스트가 자체 sitecustomize를 가져오면 그 테스트는 정직하게 측정 불가로 기록됩니다.
- 머신 간 기록 공유는 먼저 신뢰하는 머신 목록을 설정해야 합니다(고급).
