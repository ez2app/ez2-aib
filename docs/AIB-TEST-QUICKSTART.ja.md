# `aib test` 入門：変更のあったテストだけを再実行する

> 初めて使う方向けです。一言でいうと、**テストが読んだファイルも実行環境も何ひとつ変わっていなければ前回の緑の結果を再利用し、赤は必ず再実行し、計測できないものは必ず再実行します。**
> そのため、判断を誤った場合の最悪の損失は「節約できない」ことだけです。壊れたコードを正常と報告することはありません。

## 1. 実行方法

```bash
aib test tests/test_foo.py tests/test_bar.py      # これらのテストを実行（可能なものは再利用）
aib test --fresh tests/test_foo.py                # 今回はすべて実際に実行（結果は記録される）
aib test --why tests/test_foo.py                  # 実行せず、再利用されるかどうかと、どのファイルが妨げているかだけを表示
aib test --repo ~/my-project tests/test_x.py      # 別のリポジトリで実行
aib test --estimate                              # 実行せず、このリポジトリの直近 50 コミットからコミットあたりの節約量を見積もる（事前に 1 回の実行が必要）
```

テストごとに 1 行表示されます：`✓ … (reused the last green result)`、`▶ … running`、`└ green` / `└ ✗ RED`。最終行は合計です。赤のテストの出力は最後の表の下に表示されます。

### 自分のプロジェクトで使う（専用の仮想環境がある場合）

```bash
cd ~/my-project
source .venv/bin/activate                          # または：リポジトリに .venv/ か venv/ があれば自動的に使われるので、activate は不要
pip install pytest -e .                            # プロジェクトとテストに必要なものをすべてこの環境にインストール
aib test --repo . tests/test_*.py
```

使われる python の優先順位：`AIB_TEST_PYTHON=<path>` > リポジトリの `.venv/` または `venv/` > activate 済みの `VIRTUAL_ENV` > aib 自身のもの。
aib 自身の python 以外を使う場合は、開始時に次の行が表示されます：`ℹ Test python: … (version …; pytest …; from: …)`。
その python のバージョンと pytest の有無は「実行環境」に含まれ、変わるとすべて再実行されます。パッケージのアップグレードも同様です（読み込むパッケージのファイルが変わるため）。
実測（itsdangerous、テスト 5 件）：1 回目 3.2 秒ですべて実行、2 回目 0.4 秒ですべて再利用、`signer.py` を 1 行変更 ⇒ 5 件すべて再実行。

外部プロジェクトでの実測（10 件。いずれも pytest を直接実行した場合と赤／緑が一致）：itsdangerous、markupsafe、more-itertools、click、dateutil、
Flask（19.5 → 5.3 秒）、requests、django-taggit（46 → 12 秒）、pytest-xdist（99 → 74 秒）、humanize（12 → 2.4 秒）。
いずれもライブラリで、計測はすべて Linux のみです。

## 2. 対応しているテスト

| 種類 | 実行方法 | 状態 |
|---|---|---|
| Python、ファイル末尾が `if __name__ == "__main__":` | 直接実行 | 安定 |
| Python、pytest 形式（上記ブロックなし。`class TestXxx:`、`async def test_` を含む） | その python に pytest があれば pytest、なければ小さな組み込みランナーが `test_*` 関数を実行 | 利用可。pytest の fixture を使っているのに pytest が未インストール ⇒ 赤とし、インストールを促すメッセージを表示 |
| Node（`.js` `.mjs` `.cjs`、`node:test` を使用） | `node <file>` | 初版（共通の受け入れケース 12 件すべて合格） |
| jest / mocha を使う JS/TS（ルートの package.json から検出。`node_modules/.bin/` のインストールが必要） | jest：`--runInBand --no-watchman`、1 ファイルずつ。mocha：`mocha <file>` | 利用可（luxon（テスト 23 件）と cliui で、フレームワークを直接実行した場合と赤／緑が一致。2 回目はすべての緑が再利用された） |
| vitest を使う JS/TS | `vitest run --pool=forks <file>` | 正しく実行されますが**計測できないため毎回再実行**：vitest 4 / vite 8 はトレーサーから見えないネイティブコードでファイルを探索するため |
| bash スクリプト（Python/Node のテストから起動されるもの） | 親プロセスに従う | 安定 |
| Go（リポジトリのルートに `go.mod`、`*_test.go`） | `go test ./<that file's directory>`、Go 自身のキャッシュ（このマシンの実際の GOCACHE / GOMODCACHE）を使用 | 利用可（google/uuid：テスト 1 件あたり約 0.25 秒。コードを壊す ⇒ すべて赤）。パッケージ単位で動作し、同じディレクトリのファイルは赤／緑が連動します。モジュールは事前にダウンロードが必要です（`go mod download`） |
| PHP（composer.json に phpunit、`tests/` 配下の `*Test.php`） | `php vendor/bin/phpunit <file>`（先に `composer install` を実行） | 利用可（sebastian/diff、テスト 17 件、phpunit を直接実行した場合と赤／緑が一致）。トレーサーが読み取れない ⇒ 常に実際に実行 |
| その他の言語（Ruby、Rust、Java…） | `.aib/ship.toml` に宣言：`[test]` `files = ["spec/**/*_spec.rb"]`、`command = "bundle exec rspec {file}"`（`{file}` はそのテストの相対パスに置き換えられます） | トレーサーが読み取れない ⇒ 常に実際に実行しますが、パッケージのプッシュ、リリース、理由ランキングはすべて機能します。Ruby（minitest/rspec）、Go、JS では「何も実行されなかった」という要約行を認識 ⇒ 未検証として表示（minitest で確認済み） |

## 3. 結果が再利用される場合と、必ず再実行される場合

必ず再実行される場合：
- 前回が赤、タイムアウト、または不安定（同じ条件で赤になったことがある）だった。
- テストが読んだファイルの内容が変わった、一覧を取得したディレクトリでファイルが増減した、または探して見つからなかったファイルが存在するようになった。
- 実行環境が変わった（言語のバージョン、環境変数、パッケージのロックファイル）。
- ネットワークにアクセスした、または計測できないプログラムを起動した（フックのない言語、kill された子プロセス）。
  データベース：C で書かれたドライバー（psycopg2、mysqlclient、grpc、pyzmq、pycurl…）は Python の socket を経由せずに独自に接続するため、
  読み込んだだけでネットワークにアクセスしたものとみなします。（以前のバージョンではこれを見逃しており ⇒ データベースの内容が変わっても結果が再利用されていました。）Pure Python のクライアントは socket を経由するため、以前から検出されていました。
- 記録の有効期限が切れた：初回は 3 日。再実行して緑のままなら期間が倍になり（6 日、12 日）、最大 14 日です。
- テストが読んだファイルに日付が含まれ、前回の実行以降にその日を過ぎた。

**翻訳ファイルは文字列単位で追跡されます（設定不要）**：プロジェクトが gettext で翻訳している場合（Django、Flask-Babel、babel はいずれも該当）、
gettext 経由でのみテキストを参照するテストは、**実際に使った文字列**が変わったときだけ再実行されます。ほかの文字列の編集や新しい文字列の追加 ⇒ 再利用されます。
テストが .mo ファイルを直接読む、カタログ全体を列挙する、または翻訳ファイルが壊れている場合 ⇒ 従来どおりファイル全体として扱います（再実行）。.mo は .po からコンパイルされるため、.po を編集したら先に .mo を再コンパイルしてください。

辞書を JSON で管理し、独自の参照関数を書いているプロジェクト：どのファイルが辞書かを `.aib/ship.toml` で宣言します（パターンはリポジトリのルートからの相対パス）：

```toml
[test]
keyed_files = ["locales/*.json"]
```

以降、テストがこれらのファイルを `json.load` / `json.loads` で読み、一部のキーだけを使う場合 ⇒ そのキー（その下の値ツリー全体を含む）が変わったときだけ再実行されます。
全体を比較・列挙・コピー・文字列化する場合や、パース前に内容が加工された場合（例：Windows の改行コードの変換）⇒ 従来どおりファイル全体として扱います。宣言していない JSON は常にファイル全体として扱います。

## 4. 3 つのスイッチ

- 今回はすべて実際に実行する：`AIB_TEST_NO_REUSE=1 aib test …`
- 特定のテストを常に実際に実行する：テストファイルの先頭 40 行以内に `# aib: always-run` を書く
- このマシンでできないものは実行しない（「⊘ 未検証」として表示され、緑にも赤にも数えません）：テストファイルの先頭 40 行以内に次のように書く
  `# aib: needs darwin`、`needs linux`、`needs ipv6`、`needs tool:<program>`、`needs repo:<name of a sibling repo>`
  ★ 条件に書けるのはテストの*前提条件*だけで、*テスト対象そのもの*を書いてはいけません。そうしないと、それが欠けているときにテストを飛ばすことで問題を隠すだけになります。

## 5. 「未検証」は必ず見える

- `⊘ … (unverified: this machine lacks …)`：このマシンに前提条件が欠けているため実行しませんでした。要約表に独立した行として表示され、バッチは終了コード 4 で終わります。
- `⊘ N cells skipped, unverified`：緑のテストにスキップされたケース（`skip`）が含まれています。要約表に独立した行として表示されます。
- 終了コード：0 すべて緑、1 一部が赤、3 記録が保存されなかった、4 一部が未検証。

## 6. main へのプッシュとリリース：`aib ship`（どのプロジェクトでも使え、設定不要）

ユーザー向けのわかりやすいガイド（毎回何が表示されるか、どう読むか、どうすれば最も節約できるか）：`AIB-SHIP-FOR-USERS.ja.md`。

```bash
cd ~/my-project
aib ship init                     # 初めての方の最初のステップ：プロジェクト名とツリーを表示し、バージョンとテストを探し、テストがこのツリーをテストしているか確認し、
                                  #   すべてを 1 回実行して記録を作り、今後の節約量を見積もり、最も多くのテストに影響するファイルを一覧表示します。
                                  #   プッシュもコミットもしません（--no-run は検出のみ）
aib ship package --preview        # 実行もプッシュもしない：再利用が見込まれるテスト数、所要時間、主な原因となるファイル
aib ship hotfiles                 # 多くのテストに読まれ、頻繁に変更される 10 ファイル（読むテスト数 × 最近の変更回数）：これらの変更を 1 回のプッシュにまとめると最も節約できます
aib ship package                  # origin の main にパッケージを 1 つプッシュ：バージョン規則 → 修正にはテストが必要 → プッシュ前チェック → プッシュ
aib ship watch                    # 開発中は起動したままに：保存をやめて 10 秒後にミラーツリーでテストを実行（作業ディレクトリには触れません）。プッシュ時にその結果を再利用します
aib ship stats                    # 初回実行以降の累計（テスト／ケースの総数、実行ごと・週ごとの実際の節約量）＋ プッシュで最も節約できるタイミングと取るべき行動
# プッシュ前チェックは最初に比較を表示します：aib なしの場合（1 件ずつ順に実行）の所要時間、このマシンで aib を使った場合の所要時間（と終了予定時刻）、マシンを増やした場合の予測。
#   終了後に精算します（並列実行による節約／シャドウレジュームによる追加の節約）
aib ship stats --all              # このマシン上のプロジェクトごとに 1 行（テスト／ケースの総数、プッシュ回数、節約量）＋ 総合計
aib ship audit                    # 「再利用された」テストの一部を実際に再実行して結果を比較（再利用は正しいか）。結果は累計に加算され、週ごとに表示されます
aib ship stale [--run]            # 7 日以上実際に実行されていないテスト（プッシュ前チェックは影響を受けるテストだけを選ぶため、触れられないテストは長期間実行されず、赤が潜むことがあります）。
                                  #   --run でまとめて実行します。週 1 回を推奨（ある一括実行では、5 件がずっと赤のままで、14 件がクラウドで一度も実行されていなかったことが判明しました）
aib ship why                      # 「毎回再実行が必要な」テストを理由ごとにランキング（件数、1 回あたりの所要秒数）し、わかりやすい説明と対処法を表示
aib ship crosscheck               # スイート全体と照合：aib はテストを 1 件ずつ実行します。これはまず 1 件ずつ実行し（可能なものは再利用）、次にプロジェクトの通常の方法でスイート全体を 1 回実行し、
                                  #   ファイルごとに赤／緑を比較します。不一致 = テスト同士が影響し合っている（共有状態、実行順序）ため、aib の緑は CI の全体実行が緑になることを意味しません。
                                  #   pytest、jest、vitest、mocha に対応。終了コード 0 一致 / 1 不一致 / 4 比較不能。週 1 回を推奨
aib ship check                    # main の履歴に規則違反のコミットがないか確認（CI 用）
aib ship release --version 1.4.0  # 端末の前の人間のみ：まずプレビューし、バージョンを入力して初めてリリース
aib ship package --emergency      # 端末の前の人間のみ：理由を入力してプッシュ前チェックを 1 回だけ省略。次のパッケージは自動的に検証され、それまでリリースはできません
```

- **どのファイルをテストとみなすか**：Python では `tests/` 配下の `test_*.py`、`*_test.py`、`test-*.py`。**pytest で `testpaths` が設定されていれば、そのパスだけが対象です**
  （例：Flask の `examples/` は別途インストールするサンプルで、pytest もそもそも実行しません）。JS/TS（リポジトリのルートに `package.json`）では `*.test.*`、`*.spec.*`、
  `__tests__/` 配下のファイル。mocha プロジェクトでは `test/` 直下の `.js/.mjs/.cjs` も対象です。
- **バージョンを自動で探す場所**：`VERSION` → `pyproject.toml` → `package.json` → `setup.cfg` → 単一の `__version__`。
  最初のプッシュで見つかった内容を `.aib/ship.toml` に書き込み（そのパッケージに 1 コミットとして追加）、以降はそのファイルに従います。このファイルは編集できます。見つからない場合 ⇒ リリースはできませんが、パッケージのプッシュは通常どおり行えます。
- **パッケージでバージョンを変更してはいけません**。変更するのは `release`（人間）だけです。そのため通常のプッシュでは影響を受けるテストだけが実行され、バージョンはまとまりごとに 1 回上がります。
- **コードを変更したのにテストを変更していない ⇒ プッシュしません**。ただし、コミットメッセージに `No-Test-Reason: <reason>` という行がある場合は除きます（純粋なリファクタリング、テキストのみの変更）。
- **プッシュ前チェック**：失敗しそうなテストを先に実行し、最初の赤で止まります。**赤が 1 つでもあればプッシュをブロックします**（例外：aib 自身のリポジトリでは、main でも赤である古い赤は通します）。
  新たな赤は同じコードでもう一度実行し、緑になれば「不安定」とします（それでもプッシュはしません）。最後に最も遅い 10 件のテストと推定節約量を表示します。
- **再起動後は同じコマンドをもう一度実行してください**：同じコードですでに緑になったテストは再実行されません。
- **テストしたものがプッシュするコードでない ⇒ プッシュしません**：テスト用の python がこのツリーの外からパッケージを読み込んでいる場合（共有 venv、別のクローンを指す `pip install -e`）⇒
  プッシュ前チェックはすぐに「未検証」と報告します。プロジェクト専用の `.venv` を作って `pip install -e .` するか、`AIB_TEST_PYTHON` を設定してください。
  `pip install -e .` でインストールしたプロジェクトはパッケージをプッシュできますが、`aib ship watch` は使えません（ミラーツリーではミラー内のコードをテストできず、その旨が表示されます）。
- **問題のあるリリースを出してしまった場合**：問題のコミットを `git revert` して 1 つのパッケージとしてプッシュし（修正にはテストが必要という規則は引き続き適用されます）、その後、人間が次のバージョンをリリースします。バージョンを戻してはいけません。

## 6.5 CI での再利用：GitHub Actions の時間を節約する

GitHub のマシンは分単位で課金され、時間はすぐになくなります。自前のマシン（self-hosted runner）がなくても節約できます。コマンド 1 つでワークフローファイルを生成します：

```bash
aib ship ci            # .github/workflows/aib-test.yml を書き出す（既存のファイルは上書きしない。--force で書き直し、--print は表示のみ）
```

実行は引き続き GitHub のマシンで行われ、次の方法で節約します：

| 節約できる箇所 | 方法 |
|---|---|
| 影響を受けていないテストは実行しない | aib の記録プールを GitHub のキャッシュに保存し（同じブランチを優先、次にデフォルトブランチ）、次回の実行で前回の緑を再利用します |
| 不要な実行は行わない | デフォルトブランチへのプッシュと PR でのみ実行。`docs/` や `*.md` だけの変更では実行しません。同じブランチに新しいプッシュがあれば古い実行はキャンセルされます |
| インストールも安くなる | pip / npm のダウンロードをキャッシュします（小規模なプロジェクトでは、時間の大半がテストではなくインストールに使われます） |
| 節約量が見える | `aib test --all` の後、各実行の要約ページ（Actions の Web ページにあるその実行の Summary）に「aib なし → aib あり」が追加され、さらに 3 行が加わります：**課金時間（分）**（GitHub はジョブごとに 1 分単位で切り上げるため、小規模なプロジェクトでは秒は節約できても課金時間は減らないことがよくあります）、「再利用」の意味、今回実際に実行されたテスト |

**他の人からの PR（aib を使わないコントリビューター）**：
- コントリビューターは aib をインストールする必要はありません。要約ページには次のように表示されます：「再利用 = このテストが読むファイルがすべて変わっていないため、前回の緑がそのまま有効です。変更されたテスト、新しいテスト、前回赤だったテストは必ず実行されます。」
- **PR はキャッシュを読むだけで、書き込みません**：書き込むのはデフォルトブランチへのプッシュと週 1 回の全体実行だけです ⇒ 多数の PR によって main の記録が押し出されることはありません。
- **フォークからの PR は aib を使わず、通常の方法ですべて実行します**（`python -m pytest` / `npm test` / `go test ./...` / `vendor/bin/phpunit`）：
  フォークはシークレットを取得できません。また、PR のテストコードは記録プールと同じマシンで実行されるため、記録ファイルを書き換えてその実行での「再利用された緑」を偽装できてしまいます。
  main は影響を受けません（main は PR が書き込んだキャッシュを読めません）が、レビュアーには偽の緑が見えてしまいます ⇒ フォークでは再利用しません。
- **毎週日曜日にすべてを 1 回実際に実行します**（`--fresh`）：所要時間を更新し、「長期間の再利用で隠れていた」ときどき赤になるテストを見つけます。

CI の 2 回の実行をシミュレーション（毎回同じパスに新しくクローンし、実行間で記録プールを運ぶのはキャッシュのみ。itsdangerous、テスト 5 件）：
1 回目 6.5 秒（すべて実行し記録を作成）→ 2 回目 0.9 秒（5 件すべて再利用。要約ページに「待ち時間 3.8 秒短縮、約 81%」と表示）。累計はキャッシュとともに引き継がれます。
**実際の GitHub Actions ではまだ実行していません**（ローカルでのシミュレーションのみ）。

- `aib test --all`：aib ship と同じ方法で見つけたすべてのテストを実行します（pytest の testpaths、JS/Go/PHP、`.aib/ship.toml` の宣言）。
  **テストが 1 件も見つからない場合 ⇒ 終了コード 2**（何もテストしていないのに CI が緑になってはいけないため）。
- aib 自体は 1 つのコミットに固定されます（ファイル内の `AIB_REF`）。aib の新しいバージョンではすべての記録が一度無効になるため、固定しないと aib を更新するたびにすべてが再実行されます。
  手元の aib に GitHub へ未プッシュのコミットがある場合 ⇒ 書き出しません（CI が取得できないため）。aib のリポジトリが非公開の場合 ⇒ プロジェクトの Settings → Secrets に `AIB_TOKEN` を追加してください。
- インストール行（`pip install -e . pytest` のようなもの）は推測です。プロジェクトに合わせて変更してください。
- **パスは同じでなければなりません**：aib はリポジトリを git ディレクトリの実パスで識別します。GitHub Actions と GitLab CI は毎回同じパスにチェックアウトします。
  独自の CI で毎回異なるディレクトリ名を使う場合、何も再利用されません（結果は正しいままで、節約できないだけです）。
- **他のブランチが書き込んだキャッシュを main に使わせないでください**：記録プールの「前回の緑」こそがテストを省略できる根拠です。GitHub のキャッシュはブランチごとに分離されており
  （main は PR が書き込んだキャッシュを読めません）、生成されるファイルはそれを前提にしています。他の CI システムではご自身で確認してください。
- 赤の実行もキャッシュされます（赤の行は必ず再実行され、緑のテストは次回再利用できます）。
- キャッシュのない初回 ⇒ すべて実際に実行します。マシン環境が変わった場合（python のバージョン、パッケージ、GitHub のランナーイメージの更新）⇒ ローカルと同様にすべて再実行します。
- GitHub のキャッシュにはリポジトリごとの容量上限があり、しばらく使われないエントリは削除されます。削除されると、次回の実行ではすべて実際に実行されます。

## 7. 未対応／注意事項

- テストが**時計だけを読みファイルを読まない**時間依存（例：「30 日より古ければ期限切れ」）は記録の有効期限でしかカバーされないため、気づくまでに最大 14 日かかることがあります。
- Node：worker_threads とネイティブアドオン（`.node`）は常に計測不能として扱います。コンパイルキャッシュ経由で実行する TypeScript は未検証です。
- **自分でファイルを読む C ライブラリ**（Python の open を経由しないため、トレーサーから見えない）：対応済みのものは lxml（parse/iterparse）、OpenCV（imread）、
  pyarrow（parquet/csv/feather/dataset の読み込み）で、パス指定で読まれたときにそのファイルを記録します。h5py、netCDF4、PyTables、GDAL/rasterio/fiona、soundfile
  は読み込まれた時点で計測不能として扱います（毎回再実行）。
  **一覧にない C 拡張**：Linux で C コンパイラがある場合、aib は各テストプロセスに小さなライブラリ（安全網、LD_PRELOAD）を組み込み、C レベルでのファイルオープンを記録して
  事後に比較します。「Python が記録していないリポジトリ内のファイルを C レベルで読んだ」⇒ そのテストは毎回再実行されます（`aib ship why` がファイル名を示します）。
  macOS、コンパイラがない場合、または Go のように libc を経由しないプログラム ⇒ 安全網はなく、一覧にない C 拡張は既知の制限として残ります。無効にするには：`AIB_NATIVE_GUARD=0`。
  Node プロセスも比較されます。ただし Node はモジュール解決時にフックを経由せず `node_modules/**/package.json` を読むため、その部分はロックファイルに任せています（ロックファイルが変わればすべて再実行）。
  **ロックファイルを変えずに node_modules 内のファイルを手で編集した場合**、aib が気づかないことがあります（既知の制限）。
- Windows には対応していません。
- git を呼び出すテスト：履歴の読み取り（log/show/cat-file/ls-tree…、リビジョンが HEAD の祖先であるもの）、作業ツリーの読み取り（status/diff/grep）、設定の読み取り、
  ブランチ／タグの指定はすべて計測できます。リポジトリを変更するもの（commit/add/checkout…）、別のリポジトリを対象とするもの、`--ignored` のようにリポジトリ外を読むものは計測不能として扱います。
- PYTHONPATH を丸ごと置き換えてから python のサブプロセスを起動するテスト：トレーサーは自動的に末尾に自身を追加します。テストが独自の sitecustomize を持ち込む場合、そのテストは正直に計測不能として記録されます。
- マシン間で記録を共有するには、先に信頼するマシンの一覧を設定する必要があります（上級者向け）。
