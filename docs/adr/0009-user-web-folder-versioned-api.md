# ADR 0009 — Pages come from the user's folder; aibd guarantees only the versioned API

- Status: proposed (owner's decision 2026-11-14: users edit their own pages, an edit does not
  go through CI, aibd guarantees the versioned API)
- Deciders: @a9136 (aibd side), @519d0 (specification), the owner (approval)
- Supersedes: ADR 0006 section 6, in part (listed under "What changes in ADR 0006")
- Keeps: ADR 0006 sections 1–5 and 7, ADR 0003 in full
- Scope: where the page files come from, how aibd serves them, and what a page may rely on.

## Context

ADR 0006 section 6 compiles the page files into aibd and makes an open page reload whenever
the aibd build changes. The owner decided on 2026-11-14 that users edit their own HTML pages
and that an edit does not go through CI. That makes the page a file on disk that aibd has
never seen before, so two things have to be written down: what aibd promises to any page, and
what aibd refuses to serve.

A page file in the user's folder can be changed by any program running as the same OS user,
including an AI seat. So a page is not trusted more than a seat is.

## Decision

### 1. Two layers

- **aibd** (Rust, goes through CI): processes, seats, sessions, messages, permissions, events,
  and the contract of `/api/v1`.
- **Pages** (the user's folder, no CI): HTML, JS and CSS under `web/` in aibd's data directory
  (Application Support on macOS, `%APPDATA%` on Windows). aibd reads them when asked. A file
  that is not there is served from the built-in set.

The built-in pages use only the public `/api/v1`. They have no private route.

### 2. What a page may rely on

- `/api/v1` only adds: fields and routes are added, never changed or removed. An enum may gain
  a value, and a page must cope with a value it does not know. A breaking change is a new
  `/api/v2` served side by side.
- `GET /api/v1/version` returns `{build, api, capabilities, security_epoch}`. A page decides
  what to show from `capabilities`, never from the build string.
- `GET /api/v1/openapi.json`, `GET /api/v1/docs` and `GET /api/v1/sdk.js` are generated by aibd.

### 3. No forced reload on a new build

- A page no longer reloads because `X-Aibd-Build` changed. The header stays, for diagnosis.
- `security_epoch` is an integer stored by aibd and raised only by the release process, never
  by a run-time call. It is raised for a fix to the credential format, the guard, or the page
  policy. Every `/api/` response carries it in `X-Aibd-Security-Epoch`. A page that sees a
  value different from the first one it saw does a full reload.
- **Credentials are not touched by this ADR.** ADR 0006 section 7 stands: when aibd restarts,
  every page credential is invalid and the browser pairs again.

### 4. What aibd serves from `web/`, and what it refuses

1. The resolved path must be inside `web/`. `..`, an absolute path, and a file or directory
   that is a link to somewhere outside are `404` (resolve first, then compare the prefix).
   On Windows a backslash, a drive letter, an alternate data stream (`:`) and a reserved
   device name are also `404`.
2. Only these extensions are served: `html`, `js`, `css`, `json`, `svg`, `png`, `jpg`, `webp`,
   `woff2`, `ico`. aibd sets `Content-Type` from the extension and sends
   `X-Content-Type-Options: nosniff`.
3. A user file never replaces a route of aibd: everything under `/api/`, the pairing exchange
   page, the docs page and `sdk.js` are always produced by aibd. A file such as
   `web/api/...` is not served.
4. The pairing exchange page is never read from `web/` (it carries a credential).
5. A file larger than the limit is `413`. The limit is a constant.
6. A change takes effect on the next request: aibd compares the modification time and sends a
   strong `ETag` with `Cache-Control: no-cache`. aibd does not watch the folder and adds no
   timer (ADR 0005).
7. Files are sent as they are on disk: no template, no substitution. Every caller gets the
   same bytes, so **no page contains a token** — the rule and its test from ADR 0006 stay.

Each of the seven lines has a knife test.

### 5. Page policy

Every `text/html` response, built-in or from `web/`, carries:
`default-src 'self'; script-src 'self'; style-src 'self'; connect-src 'self';
img-src 'self' data:; font-src 'self' data:; form-action 'self'; base-uri 'none';
object-src 'none'; frame-ancestors 'none'`.

So a user page puts its script in a separate `.js` file. Inline `<script>` does not run.

### 6. Safe mode

- The built-in pages are always reachable under `/builtin/`. A user file cannot shadow that
  path.
- A local command switches aibd to serve only the built-in pages, and back.
- There is no URL parameter for it.

### 7. What this does and does not protect

- The page policy stops a page from sending data elsewhere with `fetch`, `XMLHttpRequest`,
  `WebSocket`, `EventSource` or a form. It does **not** stop a full-page navigation to another
  site. This is a boundary, not a defence.
- Writing to `web/` means running code with a paired page's credential. A program running as
  the same OS user can already read the launch token, so this is not a new hole, but it must
  be stated.
- Therefore a dangerous action is never decided in a page. The API answers
  `202 {approval_id}`; consent is the OS dialog with Touch ID or Windows Hello; the page only
  sees the result event. No change to a page can widen this.

## What changes in ADR 0006

| ADR 0006 section 6 | After this ADR |
|---|---|
| Files compiled into aibd (cargo feature `web`) | Built-in files stay compiled in; `web/` is read at run time |
| Page reloads when `X-Aibd-Build` changes | Reloads only when `security_epoch` changes |
| Hashed file names with `immutable` | Built-in files only; user files are `no-cache` with a strong `ETag` |
| Page policy: `self` for scripts, styles, connections, fonts, images | Kept, plus `form-action`, `base-uri`, `object-src` |
| "every static file is identical for every caller" | Kept, and now also covers user files |
| Hash routes only, unknown path is `404` | Kept |

ADR 0003 still describes a cookie for browser pairing in two places; ADR 0006 section 7
removed the cookie. Those two sentences are corrected in the same change.

## Not decided here

- The size limit, and where the shortcut to `web/` is placed.
- Sharing a page between users (not in the first version).
- Whether a desktop shell is needed later.
- Windows: the path rules in section 4 are UNVERIFIED on a real Windows machine until tested.

## Consequences

- A user can change a page and see it on reload. aibd's CI does not cover user pages.
- A broken user page cannot lock the user out: `/builtin/` and the local command remain.
- aibd gains one file-serving path whose rules must each be tested.
